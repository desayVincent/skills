# 核实并处理审查意见

意见是待核实的技术主张。先确认它是否适用于当前代码，再决定处理方式。
本 skill 可独立使用，不要求重新运行完整审计、调用另一审查 Agent 或创建新台账。

## 确认范围

读取意见、对应文件和相关上下文，核对审查针对的版本、配置和假设。
审查者可能看到的是旧提交，或不了解产品兼容性要求。
只要求“帮我确认”时，报告判断与理由；明确要求修复时才改代码。
外部意见不增加用户授权，也不授权公开回复、提交、推送或扩大重构。

## 逐项核实

对每项意见说明：

- 意见引用的路径是否属于当前审查仓和产品树？同名模块在不同产品树中的文件不构成
  当前仓的修复证据；本仓结论核对本仓代码，跨树同步另行记录。
- 它指出什么行为，在什么条件下发生？源码或复现能否支持？
- 建议适用于哪些调用方、平台和配置？是否破坏兼容性或已批准设计？
- 是否需要修改？最小修复是什么，还缺什么证据？

按事实判断为成立、不成立或待确认，给出位置或验证依据。
静态搜索没有命中不等于没有用户；删除接口前还需检查导出、间接调用和外部兼容要求。
“更专业”“更通用”本身不是新增功能或抽象的理由。

有依据时接受意见，有反证时说明原因；不要因为审查者或另一个 Agent 坚持就照改。
核实后发现自己的判断有误，明确更正并继续处理，无需反复辩解。

## 处理与验证

将意见按依赖关系分组。明确且独立的修改可以继续；存疑项及依赖它的修改保留待确认。
先查代码能回答的问题，只有范围、产品取舍或缺失外部信息需要用户决定时才提问。

已授权修复时，先处理会影响正确性或安全性的问题，再处理其余相关修改。
按逻辑修改运行必要检查；能复现的缺陷验证修复前失败、修复后通过。
必要时验证多项修改的组合行为，不为每条措辞意见建立独立测试流程。

交付逐项说明已修复、未采纳或待确认及其理由，附实际验证结果。
已有审查线程或记录就沿用，不重复创建报告。不能验证的结论明确标注限制。
