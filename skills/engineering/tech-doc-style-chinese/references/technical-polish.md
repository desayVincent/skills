# 技术写作主流程

内部技术方案、架构/设计、评审稿、复盘、性能汇报和技术分享使用本文件。它落实 SKILL.md 第 1、2、4 步；句段修复见 [表达修复](plain-language.md)，表达模式见 [模式检查](ai-patterns.md)，均由入口按条件加载。

## 1. 从读者的问题建立主线

先用一句话确定读者需要理解、决定或执行什么；可从用户要求和现有材料确认时不重复询问。维护在工作记录中，不强制把问题清单塞进正文。

| 读者任务 | 正文优先回答 |
| --- | --- |
| 开发者理解现状 | 入口与主流程是什么，谁处理数据，状态/资源何时变化，失败后怎么办 |
| 评审者选择方案 | 现有问题及约束是什么，候选如何满足它，代价和未验证假设是什么 |
| 负责人阅读结果 | 在哪些条件下得到什么结果，影响什么决定，剩余限制与待办是什么 |
| 排查者阅读复盘 | 发生了什么，证据如何支持原因，处置是否已验证，还有哪些未知项 |

先列章节承担的问题，再检查现有材料是否回答。背景只保留理解问题所需的变化和约束；不按聊天轮次或作者调查顺序堆叠。

完成条件：每个主要章节有明确用途；材料不能回答的问题保持待确认，不能靠增加通用背景填满。

## 2. 先核对主张，再组织论证

标出最强的判断：根因、性能改善、可靠性保证、方案优越性、已实现能力。为每项找到已有来源和适用条件，随后区分：

- 观察：代码、trace、日志、实验或用户材料实际呈现了什么。
- 推断：观察支持怎样的解释，还有哪些替代解释或反例。
- 决定：谁已批准什么选择，其理由、代价和边界是什么。
- 状态：当前已实现、计划实现、候选、待验证分别是什么。

这几类信息不必逐句贴标签，但语义不能混用。引过来源不等于结论成立；来源必须支持对应主张。多次重复一个猜想也不构成交叉验证。

原文没有证据的「已显著提升」不能仅删成「已提升」并当作确认结论。保留「原文称……，现有材料未提供对比结果」或在允许纠正的范围内改为待验证，并列出缺口。

完成条件：关键判断能追到证据或已明确标为未确认；因果、范围、测量与预期不互相替代。

## 3. 用解释推进章节

内部技术长文的默认思路是：问题与背景 → 现状及约束 → 待回答的问题/假设 → 分节解释 → 实现影响 → 验证与限制。已有正式模板和短文按实际任务裁剪，不强制新增所有章节。

摘要可以先给已有依据的结论，紧接适用条件、主要证据和影响；有待批准的方案就写「建议」，不要写成决定。摘要不复述目录或预告写作动作。

每节先说明当前问题及已有答案，再用证据或机制支持，最后仅在确有内容时说明影响或未解决问题。段落能任意调换且仍无影响时，检查是否只是重复观点；独立的参考条目可以互换，不必制造连接。

介绍模块时同时连接两层：

- 设计层：用途、边界、选择理由与约束。
- 实现层：已有材料中的入口、模块、接口、数据、状态和可观测结果。

只在影响理解时解释线程、缓冲区、锁、DMA、协议等，不把它们变成通用必填表。源码名称不证明关系；具体责任没有证据时写明缺口。

连续机制用段落，执行顺序用编号步骤，可独立比较的参数/方案用表格。不要把整段说明塞进宽表；必需列、稳定 ID 和绑定关系保留，长解释移到邻近小节并链接。已有图帮助说明拓扑/时序时结合正文；新增或改图须在授权内，不为了完整感强制绘图。

完成条件：读者能从问题追到机制、依据和影响；只有抽象概念或源码名字时继续解释，不补造关系。

## 4. 按文档目的保留关键信息

| 类型 | 必须从已有材料保留或明确缺失的信息 | 常见误写 |
| --- | --- | --- |
| 方案/设计 | 问题、约束、现状、候选与批准状态、理由、代价、影响接口、失败路径及验证 | 把提案写成现状；只列优点；从名称推断所有权 |
| 评审稿 | 待决定事项、依据、适用条件、反例或风险、未验证项 | 把作者的倾向变成评审结论；为了「平衡」发明反方 |
| 复盘 | 时间线、影响范围、可观察证据、原因/假设、处置、验证与遗留项 | 事后把线索写成确定根因；删掉失败过的关键处置 |
| 性能汇报 | 测试对象/版本、硬件与环境、负载、基线、指标及单位、统计口径、波动和局限 | 把单次结果写成稳定收益；把耗时降幅说成吞吐提升 |
| 技术分享 | 读者所需背景、核心问题、机制、可信例子和适用边界 | 用故事或比喻代替机制；凭空加入个人经历 |

不同条件的数字可以并列报告，但不能直接据此归因。必要的数值计算仅在任务授权时做，保留输入、口径和原始数据；纯文字整理不自动换算或添加收益百分比。

## 5. 更新旧文档

全文更新时保留基线，读完每个完整章节，逐节记录处理结果；工具截断则补读。局部更新只读受影响的完整小节及必要关联。

先找现行结论，再区分补充、替代和冲突。授权且已有证据确认的旧结论原位更新，同步范围内的摘要、正文、表格和引用；不同版本或配置仍然有效的结论分别保留。范围外关联位置仅报告。

正文解释当前机制，修订经过移到已有且授权的修订记录或评审报告。影响适用版本、决定理由和证据追踪的历史信息仍保留；没有合适位置时在交付说明中列明，不能直接删除或强制新建报告。

完成条件：授权范围所有章节已处理或确认无需修改；当前说明一致，未确认冲突单列。不能只补一个「新版说明」，留下旧正文与之矛盾。

## 段落级示例

输入材料：缓存只用于配置表查询；命中时直接返回缓存项，未命中时读取配置表。没有性能数据。

原文：为了实现查询能力的全面升级，该模块通过缓存机制赋能查询链路，构建了高效、稳定、可扩展的闭环。接下来我们将进一步探讨这种机制。

可用改写：配置表查询先检查缓存。命中时直接返回缓存项；未命中时读取配置表。现有材料未提供性能测量，不能确认加速幅度。

检查：改写使用给定机制，没有推断缓存写回、淘汰、线程安全或性能收益；空泛评价对应的证据缺口仍可见。若没有输入材料中的机制，不能自行生成这段改写。
