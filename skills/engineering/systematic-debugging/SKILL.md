# 根据证据定位故障

先建立可检验的根因解释，再修改实现。流程随问题规模调整，
不强制生成计划文件、固定数量的假设或整套 Superpowers 工作流。
与其他调试 skill 同时适用时，遵守用户或项目指定的入口；本流程补充缺失步骤，
不重复执行另一套复现和审批流程。

## 1. 确认故障与证据

明确预期行为、实际行为、触发条件和已知正常版本。读取完整相关错误，
检查近期源码、配置、依赖及环境变化。区分观察到的事实与推测。

尽量建立可重复运行的最小复现，并记录命令、输入和实际输出。
偶发问题记录触发次数、失败次数和测试条件；一次通过不能证明修复。
暂时不能复现时，继续分析已有日志、转储和源码，设计能区分原因的观测，
明确尚不能验证的假设。仅在缺失信息阻止下一步时请求所需环境或记录。

## 2. 定位错误来源

沿错误数据、状态或控制流向上追踪，找到最早违反预期的位置。
对照同项目的正常路径，检查真正相关的配置、调用顺序和依赖差异。
在组件交界处观察输入、输出和状态，逐步缩小范围；避免输出全部环境变量、
凭证或业务数据。新增诊断代码只服务于具体问题，并标记以便清理。

修复共享函数前，检查其调用方和相同模式的其他路径；符号引用只是线索，
不能证明不存在间接调用。不要只修报错位置而留下相同根因。

## 3. 验证假设

每次实验写清“怀疑什么、依据是什么、哪种结果支持或推翻它”。
存在多个合理解释时先比较，再优先验证区分力高且成本低的一项。
每次只改变一个可判断的因素；失败的实验不作为下一次修复的隐含前提。
连续失败或出现新症状时，重新检查假设、观测方法、环境和设计约束。
失败次数本身不证明架构错误，也不授权扩大重构范围。

## 4. 修复与验证

选择能消除已确认根因的最小修改。可执行时先运行会因原始故障失败的用例，
修复后再运行同一用例及相关回归。无测试框架时可使用小脚本、构建复现或板端步骤。
测试必须覆盖真实触发方式；主机替身通过不能代替目标环境验证。

不能执行必要验证时，交付可审阅的候选修复和具体缺口，不宣称已修复。
清理本次临时诊断代码；用户要求保留的诊断能力按其范围处理。
最终说明根因、修改、验证环境与结果、未验证范围。

## 嵌入式与受限环境（仅在相关时）

- 记录会影响故障的板卡/芯片版本、固件与构建配置、时钟及启动方式。
  区分冷启动、热启动和复位后的状态；每次实验说明如何恢复基线。
- 日志、断点或额外等待可能改变时序。选择干扰较小的观测方式，
  记录其影响；不能通过加延时掩盖故障并宣称根因已消除。
- 读取寄存器可能清状态，调试器暂停 CPU 也未必暂停外设。
  根据平台资料选择观察方法；访问、刷写和复位遵守现场授权及共享设备安排。
- 性能问题固定可比的输入和配置，记录实际分布与波动。
  区分主机、模拟器、FPGA 和目标芯片证据，不将其等同或无依据外推。
- 中断、缓存、DMA、RTOS 等机制只有在项目涉及且与故障有关时展开，
  使用对应项目资料或已安装领域 skill；缺少开发板不阻止独立源码分析。
